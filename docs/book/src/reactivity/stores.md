# Stores

`reactive_stores` is the upstream Leptos library for *fine-grained
reactivity over structs*. It's re-exported by all three native
ports.

The problem stores solve: when you have a struct with multiple
fields and you want updates to one field to trigger only the
views that read *that* field, wrapping the whole struct in a
single `RwSignal<MyStruct>` is too coarse — *every* read sees
*every* write. Wrapping every field in its own signal is too
verbose.

`Store` does that wrapping automatically.

## Basics

```rust
use reactive_stores::{Store, Patch};

#[derive(Debug, Store, Patch)]
struct User {
    name: String,
    email: String,
    admin: bool,
}

let store = Store::new(User {
    name:  "Alice".to_string(),
    email: "alice@example.com".to_string(),
    admin: false,
});

// Per-field accessors generated by #[derive(Store)]:
store.name();   // Field<String>
store.email();  // Field<String>
store.admin();  // Field<bool>
```

Each field is its own signal-like value. Reads (`.get()`) and
writes (`.set(...)`) work like normal signals. Views that read
only `store.name()` re-render only when `name` changes — not
when `email` or `admin` does.

## A worked example

```rust
use leptos::prelude::*;
use reactive_stores::{Patch, Store};

#[derive(Debug, Store, Patch)]
pub struct User {
    name: String,
}

#[component]
fn App() -> impl IntoView {
    let store = Store::new(User { name: "Alice".into() });
    let name_field = store.name();

    view! {
        <vstack padding=16.0 gap=8.0>
            <label>{move || format!("Hello, {}", name_field.get())}</label>

            <text_field
                value=move || name_field.get()
                on:change=move |s: String| {
                    store.patch(User { name: s });
                }
            />
        </vstack>
    }
}
```

This is `cocoa/examples/stores`.

## `Patch`

`#[derive(Patch)]` gives you `store.patch(value)` — it does a
field-by-field comparison and only notifies subscribers of the
fields that actually differ. Combined with `#[derive(Store)]`,
that's how a partial update can avoid pinging unrelated views.

## Nested stores

If a field's type *also* derives `Store`, you get nested
fine-grained access:

```rust
#[derive(Store, Patch)]
struct Address {
    city:    String,
    country: String,
}

#[derive(Store, Patch)]
struct User {
    name:    String,
    address: Address,
}

let store = Store::new(User { /* ... */ });
store.address().city();   // Field<String> that fans out only on city changes
```

## When to use stores vs signals

- A single value or two: just use `RwSignal<T>`.
- A struct with several independently-updating fields:
  `Store<T>`.
- A list whose item identities matter (insertion / removal /
  reorder): an `RwSignal<Vec<T>>` driving a `<For>` is usually
  fine. For very large lists where partial updates matter, stores
  + collection helpers can avoid full re-derives.

## Limitations

The `Store` / `Patch` derives expand to substantial code. If
compile times matter and your struct has many fields, consider
whether you actually need field-level pruning or could get by
with a coarser grouping (one signal per logical "section" of
state).
